# Firmware

Dukungan pembacaan adalah Linux amd64 dan arm64 dengan `fwupdmgr`. Inventaris menggunakan `get-devices --json`, sedangkan daftar kandidat memakai `get-updates --json` dan metadata lokal yang sudah tersedia. Baris `Kandidat` di CLI menandai rilis yang memenuhi syarat pemilihan UEFI capsule. JSON juga memuat metadata plugin lain. Inventaris tidak menyertakan nama akun atau nomor seri perangkat.

Versi target `ID@VERSI` dicocokkan persis dan dapat diawali huruf atau digit. Versi di luar format token rencana dipertahankan sebagai metadata tampilan. Entri semacam itu tidak menghalangi kandidat pada perangkat lain. [Format versi LVFS](https://lvfs.readthedocs.io/en/latest/metainfo.html#version-format)

Jalur tulis mendukung UEFI capsule perangkat dengan plugin `uefi_capsule` di fwupd 2.0.x. Aksi memakai ID perangkat dan versi yang dipilih, satu komponen, metadata LVFS stabil yang divalidasi fwupd, SHA-256 CAB, dan payload bertanda tangan. Mesin harus memakai daya AC yang terdeteksi. Jika kapasitas baterai tidak diketahui, UPower harus mengonfirmasi bahwa baterai tidak ada. Daemon harus memiliki `OnlyTrusted=true`. Cabang alternatif, downgrade, perangkat yang terkunci, emulasi, dan paket dengan hasil pencocokan ambigu ditolak.

Metadata dapat diminta melalui aksi refresh LVFS. Rencana memperlihatkan akses jaringan dan perubahan cache lokal. Remote unduhan aktif harus LVFS stabil dan URL metadata serta tanda tangan harus sesuai konfigurasi resmi. JSON mode fwupd melewati alur pelaporan otomatis pada perintah refresh. Pemeriksaan offline tidak mengunduh metadata ataupun firmware.

Saat fwupd 2.0.x belum melaporkan `ChecksumSig` sesudah refresh awal, whwmpc membaca hash JCat dari cache LVFS standar. Aplikasi mengikat path ke URI resmi, memeriksa kepemilikan root dan izin direktori, mencocokkan mtime metadata dengan daemon, serta memeriksa ukuran dan identitas file sebelum dan sesudah membaca. fwupd memvalidasi katalog. Pemeriksaan `trusted-metadata`, `OnlyTrusted`, dan checksum CAB tetap berlaku ketika menyusun dan menjalankan rencana. [Kode pembaruan metadata fwupd 2.0.20](https://github.com/fwupd/fwupd/blob/2.0.20/src/fu-engine.c#L4354) · [Hash cache fwupd](https://github.com/fwupd/fwupd/blob/2.0.20/libfwupd/fwupd-remote.c#L1044)

Build `9300a82` menyelesaikan refresh dari cache kosong pada fwupd 2.0.20 dengan `OnlyTrusted=true`, CA distro, dan koneksi TLS ke `cdn.fwupd.org`. Daemon belum melaporkan `ChecksumSig`, lalu aplikasi memverifikasi JCat di cache terlindung. Sandbox memiliki bus privat, nol perangkat, dan nol riwayat penulisan firmware. [Bukti refresh katalog LVFS publik](assets/fwupd-lvfs-public-refresh.json)

Setelah konfirmasi pembaruan, aplikasi mengunduh satu CAB melalui HTTPS, membatasi ukurannya, memeriksa SHA-256, dan meminta fwupd mencocokkan kembali GUID, versi, dan tanda tangan payload. Pengalihan ke `r2.fwupd.org/lvfs-prod/` hanya diterima untuk nama CAB yang sama dengan URL awal. Aplikasi memeriksa ulang perangkat, metadata, konfigurasi trust, dan daya setelah unduhan. Instalasi memakai otorisasi sistem melalui fwupd dan tidak melakukan restart otomatis. Simpan cadangan dan kunci pemulihan enkripsi saat meninjau rencana firmware. [Panduan unduhan LVFS](https://lvfs.readthedocs.io/en/latest/download.html#redirects)

Pada capsule dengan format versi `hex`, `GetDetails` fwupd 2.0.x dapat melaporkan `->convert_version not implemented` dan mengosongkan versi. Jika fwupd mengonfirmasi tanda tangan payload dan metainfo serta digest LVFS yang cocok, whwmpc memakai `/usr/bin/cabextract` untuk membaca metainfo ke stdout. Pemeriksaan mencocokkan satu ID komponen, satu GUID `flashed`, protokol capsule, dan satu versi heksadesimal 32-bit dengan rencana. `cabextract` diperlukan untuk kasus ini. Format versi dan ID komponen ikut diikat ke rencana, jadi rencana firmware yang dibuat sebelum upgrade bisa memerlukan preview ulang. [Pemeriksaan tanda tangan CAB oleh fwupd](https://github.com/fwupd/fwupd/blob/2.0.20/src/fu-cabinet.c#L528-L568) · [Format metainfo LVFS](https://lvfs.readthedocs.io/en/latest/metainfo.html#version-format)

Layar firmware menampilkan jumlah perangkat ketika inventaris berhasil dibaca. Jika platform belum mendukung fwupd atau `fwupdmgr` hilang, layar menjelaskan kebutuhan backend dan menyembunyikan pilihan katalog.

Build bersih `04876fc` membaca kandidat Lenovo Battery 1.0.8 dari katalog publik dengan perangkat ESRT sintetis. fwupd memeriksa tanda tangan, GUID, dan versi CAB setelah SHA-256 cocok. Apply yang dikonfirmasi menulis satu capsule 80.560 byte ke ESP sementara. `--resume` mengembalikan `reboot_required` dengan versi aktif 1.0.7. Uji dihentikan sebelum boot. [Bukti uji CAB publik](assets/fwupd-lvfs-cabinet.json)

CAB publik Dell Pro Max EC melewati verifikasi ketika fwupd mengosongkan versi. Metainfo yang terverifikasi memuat `0x2000d00`, setara dengan target `0x02000d00`. Apply menulis capsule 518.970 byte ke ESP sementara. Versi aktif tetap `0x02000c00` dan `--verify` mengembalikan `reboot_required`. Probe QEMU dengan OVMF Ubuntu menjalankan kueri kemampuan FMP dan mengembalikan `EFI_UNSUPPORTED` tanpa ESRT. Validasi boot capsule masih memerlukan firmware yang menyediakan FMP dan ESRT. [DxeCapsuleLib OVMF](https://github.com/tianocore/edk2/blob/edk2-stable202402/OvmfPkg/OvmfPkgX64.dsc)

Jika fwupd mencatat pending atau needs-reboot, restart sendiri sambil mempertahankan daya AC. Lanjutkan dari **Riwayat → Periksa firmware setelah restart** atau jalankan `whwmpc firmware --resume PLAN_ID`. Aplikasi menyimpan target handoff secara privat. Verifikasi mencocokkan versi rilis di `fwupdmgr get-history --json` dengan versi aktif perangkat yang dibaca ulang. Bila versi aktif hanya berasal dari perangkat emulasi, hasilnya unknown. Backend ini tidak menyediakan pemulihan firmware. [Emulasi fwupd](https://github.com/fwupd/fwupd/blob/2.0.20/src/fwupdmgr.md#emulation)

Handoff menolak rekaman `Modified` fwupd dari sebelum rencana dibuat. Hasil akhir `verified` atau `failed` menambahkan satu entri ke Riwayat dengan ID rencana yang sama, mencatat waktu verifikasi, dan menutup pilihan verifikasi untuk entri staging. Hasil menunggu atau belum pasti mempertahankan pilihan tersebut. `--verify DEVICEID@VERSI` membaca hasil fwupd tanpa menulis Riwayat lokal. [Timestamp riwayat fwupd](https://github.com/fwupd/fwupd/blob/2.0.20/src/fu-history.c#L875-L888) · [Uji handoff dan riwayat](assets/fwupd-handoff-history.json)

Hasil verifikasi di TUI menampilkan kebutuhan restart, kegagalan, atau konfirmasi versi yang sudah terverifikasi. Versi aktif tampil bila fwupd berhasil membacanya. Piko merayakan hasil ketika riwayat dan versi aktif sudah cocok.

Fixture menguji pembacaan metadata, target berubah, digest unduhan, kecocokan CAB, izin, output rusak, metadata kedaluwarsa, dan pemisahan pending, gagal, serta hasil terverifikasi setelah reboot. Host pengembangan memiliki fwupd 2.0.20. Validasi host sebatas inventaris dan pembacaan konfigurasi. Flash dan reboot pada perangkat nyata memerlukan izin khusus.

Untuk memeriksa calon perangkat uji, jalankan `whwmpc firmware --updates` dan, bila perlu, ulangi dengan `--json` untuk melihat `Plugin` per perangkat. Pada host pengembangan, `v0.3.5` membaca 16 perangkat tanpa plugin `uefi_capsule`. Ada dua rilis yang dilaporkan, masing-masing dari `uefi_db` dan `uefi_dbx`. CLI menampilkan nol baris `Kandidat`. Pada host yang memiliki kandidat, tinjau target persis yang ditampilkan dengan `whwmpc firmware --update DEVICEID@VERSION`. Perintah ini hanya menampilkan rencana.

Pada sandbox amd64, fwupd 2.0.20 memakai fixture ESRT upstream, HTTPS loopback, kunci PKCS#7 uji, ESP sementara, serta bus dan PolicyKit privat. CLI berjalan sebagai user biasa. Refresh bertanda tangan berstatus `verified` dari cache kosong. Konfirmasi salah dan perubahan AC berhenti sebelum unduhan CAB. Konfirmasi yang sah mengambil satu CAB, lalu daemon menulis capsule sintetis 4.112 B. `whwmpc firmware --resume` menunjukkan `reboot_required` pada 0.1.50. Sesudah simulasi boot, versi aktif 0.1.51 cocok dengan riwayat fwupd, capsule disingkirkan dari ESP, dan CLI mengembalikan `verified`. Uji penerapan firmware perangkat dari LVFS memerlukan perangkat kompatibel dan persetujuan khusus untuk flash serta reboot.
